# Requirements and implementation decisions

Source: the complete [original assignment](original-task.md), with a faithful [English translation](task.en.md). The implementation also incorporates the user's requirements from 16 October 2026 and the English localization and review of 23 October 2026. This document records implementation choices, rather than adding them to the original assignment.

- **Application:** Go backend, PostgreSQL, and browser JavaScript without third-party frontend packages or a build step. One Go binary serves the panel and REST API; Docker Compose starts the application and database.
- **Data model:** exactly the eight expense fields from the assignment. The seven original Russian category keys remain stable in storage and JSON. English display labels are Food, Transport, Housing, Entertainment, Health, Shopping and Other. User comments and names retain their original language.
- **Money:** one currency, RUB. Go uses integer kopecks, PostgreSQL uses `NUMERIC(11,2)`, and JSON uses decimal strings. Positive expense amounts are limited to `999999999.99`; excess precision is rejected without rounding. Totals are calculated by SQL over all matching rows and may exceed one expense's limit, within the exact `int64` kopeck range.
- **Dates:** `spent_at` is a calendar date; creation and update times are `TIMESTAMPTZ`. The server calculates yesterday, the Monday-to-today week, and the current month in `APP_TIMEZONE`. Both filter boundaries are inclusive. The panel proposes today's date in the browser's timezone.
- **Agent:** a configurable OpenAI-compatible Chat Completions client with structured tool calls. English is the default response language; input may be multilingual. The model selects limited expense operations and cannot execute arbitrary SQL, code, HTTP requests or MCP tools. Validation and ownership enforcement run on the server.
- **Ownership:** bot tools use a transaction-bound session scoped to the sender from the trusted Telegram update. They do not use the administrative REST API. Every repository operation enforces that owner, even if another user ID is supplied in an input or filter.
- **Target selection:** an ambiguous update or delete asks the user to choose an ID. The current message must select the ID, explicitly refer to the latest expense, or contain the literal search phrase. The model cannot silently narrow an ambiguous choice from history or list results. A turn may update or delete only one expense. “Latest” means last created, ordered by `created_at` and ID.
- **Concurrent corrections:** scoped `Get` and `Last` use `FOR UPDATE`, retaining the row lock until the bot turn completes. A search selector re-reads the selected row under that lock and rechecks its comment before applying a partial correction. This prevents a bot correction from replacing newer unrelated fields using stale list data. Administrative PUT remains a full replacement with last-writer-wins behavior; there is no optimistic version field.
- **Atomicity and retries:** one agent turn, its expenses, history and saved reply commit together. Turns are serialized per owner. Repeated Telegram update IDs return the saved reply; identical mutating tool calls within a turn return their cached result. Reads remain fresh. Cancellation, a provider failure or invalid later call rolls back the turn. A new Telegram message with the same text is a new intent; global text deduplication would hide legitimate repeated purchases.
- **Telegram delivery:** HTTPS long polling handles private text chats sequentially. Temporary reply failures, including HTTP 429 and 5xx, retry the same update using its saved result. Permanent send failures (HTTP/API status 400, 403 or 404) skip delivery of that update and advance polling, allowing later updates to proceed. An uncertain delivery may produce a repeated reply; it does not repeat a committed expense mutation.
- **Panel and HTTP boundaries:** the unauthenticated panel deliberately manages all users' expenses. Only a localhost port is published, and PostgreSQL has no published port. Host/Origin/Fetch Metadata checks, CSP and safe text rendering support this local setup but do not replace authentication.
- **Bounded API work:** database operations inherit client cancellation and earlier deadlines. API requests have a 10-second server budget, and health checks have a 2-second budget, including pool and lock waits. Deadline failures produce a safe HTTP 503 `internal_error` response; driver details remain private.
- **Listing:** administrative API pagination defaults to 20 rows, maximum 100; the bot lists 10 rows per page. Order is `spent_at DESC, id DESC`. Page rows and the matching count come from one SQL statement snapshot. The exact summary is a separate read and ignores pagination.
- **Configuration and scope:** missing credentials do not enable a fake production LLM. The full panel/API works without them, and real polling starts only after configuration. Fake providers are confined to tests. Family authentication, multiple currencies, retention, outbox delivery, administrative idempotency and versioned edits remain outside this assignment.
