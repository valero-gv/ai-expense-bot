# Фактическая проверка — 16 октября 2026

Проверено локально на macOS arm64 и в Docker linux/arm64. Результаты ниже относятся к выполненным командам; доступ к настоящим Telegram/LLM не подменяется mock-проверкой.

## Соответствие обязательным требованиям

| Требование | Реализация |
|---|---|
| Backend Go | `cmd/server`, стандартный net/http, pgx и PostgreSQL |
| Telegram + настоящий LLM-агент, CRUD обычным текстом | HTTPS long polling, настраиваемый Chat Completions клиент, семь structured tools; fake только в тестах |
| Каждый пользователь управляет только своими расходами | Владелец из Telegram `from.id`; scoped Session с server-side SQL scope для всех операций |
| Панель без авторизации, CRUD всех, фильтры | Встроенная responsive HTML/CSS/JS-панель: член семьи, даты, категория, комментарий |
| Панель через REST | `/api/expenses`, `/api/summary`, `/api/users`, `/api/categories` |
| Запуск всех зависимостей одной командой | `docker compose up --build`, PostgreSQL + app, автоматические миграции и healthcheck |
| Конфигурация LLM | Env base URL/model/API key/timeout; `.env.example`; секреты не входят в build |

## Живое подключение Telegram и Groq

Настроен Groq `openai/gpt-oss-20b` через `https://api.groq.com/openai/v1`, timeout 60s. Telegram `getMe` и `getWebhookInfo` успешны; webhook отсутствует. Пользователь подтвердил получение ответа на Start: первоначально это была ошибка обработки, что подтвердило настоящую цепочку получения/отправки Telegram, но не успешную запись расхода.

Живые запросы выявили две несовместимости, которые исправлены: пустая схема `latest_expense` заменена аргументом `count=1`; сокращённые примеры в системной инструкции заменены полным JSON со всеми обязательными null-полями. Все восемь примеров теперь автоматически проверяются по семи настоящим tool schemas. `/start` обрабатывается локально после проверки отправителя и не требует LLM.

Повторный живой прогон `python3 scripts/live_llm.py --no-build` — **6/6 PASS**, 12 настоящих LLM-запросов, 307 секунд с минутными паузами. Использованы финальные исходники; входящие сообщения Telegram в этом прогоне не имитировались. Клиент обращался к Groq, агент исполнял настоящие SQL-инструменты в отдельной автоматически удаляемой схеме PostgreSQL.

| Настоящая фраза | Проверенный результат |
|---|---|
| кофе 350 | Одна запись 350.00, категория еда, текущая локальная дата |
| последнее было не 350, а 450 | Та же запись изменена на 450.00 |
| такси 1200 вчера | Вторая запись 1200.00, транспорт, предыдущая календарная дата |
| сколько потратил на еду в этом месяце | Точная сумма 450.00, одна трата |
| покажи траты за неделю | Обе собственные записи, суммы 450.00 и 1200.00 |
| удали такси | Удалено только такси; кофе 450.00 сохранён |

На каждом шаге сверены фактические строки БД, отсутствие чужой суммы в ответе и неизменность контрольного расхода другого синтетического владельца. Ключи не входят в аргументы процессов, ответы и трассировку; Telegram-токен в тестовый контейнер не передаётся. После явного включения сетевого теста отсутствие конфигурации считается ошибкой; URL/timeout проверяются правилами приложения, удалённый HTTP запрещён. Максимальный общий timeout 45m покрывает разрешённые паузы.

При повторной проверке пользователь сообщил, что `/start` не отвечает: HTTP/БД оставались healthy, в логах были сбои polling, а Telegram показывал одно ожидающее сообщение. Выполнен полный перезапуск app и db с сохранением тома PostgreSQL. После запуска getMe успешен, webhook отсутствует, очередь пуста; пользователь подтвердил получение приветствия. Добавлены безопасные категории ошибок polling/sendMessage (таймаут, отмена, HTTP-статус, прочий транспортный сбой). Целевые race-тесты подтверждают отсутствие токена, URL и приватных деталей в ошибках и логах. HTTP healthcheck проверяет HTTP/БД и сам по себе не гарантирует доступность внешнего Telegram.

Пользователь отправил настоящему боту «кофе 350». Прямой SELECT из PostgreSQL и GET /api/expenses подтвердили запись #3: 350.00, категория еда, дата 2026-10-16, комментарий кофе. В открытой панели localhost:8080 эта строка видна; на момент проверки панель показывала три расхода и общий итог 1850.00. Таким образом, подтверждено сохранение настоящего Telegram-расхода и его отображение в административном интерфейсе.

Затем пользователь отправил боту «измени #3 на 450» и подтвердил получение ответа об изменении. Прямое чтение PostgreSQL и GET /api/expenses/3 вернули ту же запись с amount=450.00, сохранив категорию, дату и комментарий. GET /api/summary и открытая панель согласованно показывали три расхода и итог 1950.00; в интерфейсе кофе отображался как 450.00.

После команды настоящему боту «удали #3» пользователь подтвердил ответ об удалении. В PostgreSQL запись #3 отсутствует; GET /api/expenses/3 возвращает HTTP 404 с not_found. База, GET /api/summary и панель согласованно показывают два оставшихся расхода и итог 1500.00: бензин #4 за 1000.00 и футболка #5 за 500.00. Кофе исчез из интерфейса. Ручные создание, изменение и удаление через настоящего Telegram-бота подтверждены чтением БД/API и интерфейса.

Далее пользователь проверил настоящие Telegram-запросы «покажи расходы за сегодня» и «сколько потратил сегодня»: подтвердил список бензин 1000.00 и футболка 500.00, затем итог 1500.00 и две траты. Независимые SQL-чтение и GET /api/expenses, GET /api/summary с from=to=2026-10-16 дали те же записи, количество и точную сумму. Удалённый кофе в сегодняшний список и сумму не входит. Ручные чтение списка и агрегирование через настоящего бота также подтверждены.

Остаётся сценарий двух настоящих Telegram-аккаунтов. Изоляция двух пользователей уже проверена в автоматических PostgreSQL/agent-интеграциях; это не заменяет проверку двумя телефонами. Поведение произвольных моделей и все формулировки русского языка не проверены.

## Известные ограничения

Панель намеренно без авторизации и доступна только локально. Одна валюта RUB. Polling последователен, одна изменяемая/удаляемая запись за сообщение, короткая ограниченная история. Транзакция держится во время LLM-вызовов. Ответ Telegram может повториться при неопределённом результате доставки; расход не дублируется. Повтор нового сообщения — новый расход. POST административного API не имеет idempotency key. Production-нагрузка и произвольные LLM-провайдеры не проверялись. Подробнее — README.
